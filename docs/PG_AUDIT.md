# Beebo SQL → PostgreSQL Audit

Every SQL statement in `app/` (file:line + summary), tagged with the construct
that must change for PostgreSQL. Statements that carry no tag are portable as-is
(basic `SELECT`/`INSERT`/`UPDATE`/`DELETE` with `?` placeholders, standard joins,
standard indexes).

## Tag legend

| Tag | Meaning / PostgreSQL change |
|---|---|
| `PLACEHOLDER` | `?` positional placeholders → psycopg3 `%s` (or `%(name)s`) |
| `LASTROWID` | `cursor.lastrowid` → `RETURNING id` |
| `AUTOINCREMENT` | `INTEGER PRIMARY KEY AUTOINCREMENT` → `BIGINT GENERATED BY DEFAULT AS IDENTITY` |
| `BEGIN_IMMEDIATE` | `BEGIN IMMEDIATE` → plain `BEGIN` / transaction isolation (no SQLite single-writer analog) |
| `INSERT_OR_IGNORE` | `INSERT OR IGNORE` → `ON CONFLICT DO NOTHING` |
| `UPSERT` | SQLite `ON CONFLICT … DO UPDATE` → PG equivalent (syntax is compatible; verify `excluded.*` reference) |
| `COLLATE_NOCASE` | `COLLATE NOCASE` → unique index on `lower(col)` / `ILIKE` |
| `ROWID` | `ORDER BY … rowid` → explicit tiebreaker column (PG has no `rowid`) |
| `PRAGMA` | `PRAGMA …` → remove (FKs always on) or replace with catalog query |
| `EXECUTESCRIPT` | `executescript()` → split statements / psycopg3 has no multi-statement execute |
| `DATETIME_FN` | SQLite `datetime('now')` / `CURRENT_TIMESTAMP` semantics → PG `now()` / `TIMESTAMPTZ` default |
| `TIMESTAMP_TEXT` | `TIMESTAMP`-typed columns / `TEXT` timestamps → `TIMESTAMPTZ` |
| `LIKE_CASE` | `LIKE` (case-insensitive in SQLite ASCII) → `ILIKE` / `lower() LIKE lower()` |
| `GROUP_BY_BARE_COLUMN` | non-aggregated column in SELECT with GROUP BY (SQLite allows; PG rejects) |
| `DISTINCT_ORDER_BY` | ORDER BY expr not in SELECT DISTINCT list |
| `NULL_ORDERING` | ORDER BY on nullable col — SQLite sorts NULLs first (ASC); PG sorts NULLs last (ASC) |
| `TYPE_STRICTNESS` | mixed-type comparison / boolean-as-int (PG is strict) |
| `LITERAL_PERCENT` | literal `%` in SQL — must be `%%` once parameters are bound via `%s` |
| `READ_MODIFY_WRITE` | SELECT-then-write decided on the result, relying on SQLite's single-writer lock → needs row locking / upsert / retry |
| `DYNAMIC_SQL` | f-string SQL — confirm identifiers are whitelisted (they are, in all cases below) |

Notes for post_service.py:
- `list_posts` (377–421) builds `WHERE` from fixed string fragments; every value is a parameter, so it's safe `DYNAMIC_SQL`. The `GROUP BY quoted_post_id` at :262 has only `quoted_post_id` selected with the aggregate — no bare-column problem.
- `_toggle_like` and the like/unlike path rely on SELECT→INSERT/DELETE with a `try/except` retry on unique-violation. In PG, `INSERT … ON CONFLICT DO NOTHING` (or a unique-violation retry) is needed; the current `except Exception: rollback()` re-check works but should be tightened to catch `UniqueViolation`.

## Cross-cutting notes (not per-statement)

- **`PLACEHOLDER`** applies to essentially every statement above; it is listed on each row but the transformation is global: `?` → psycopg3 `%s` (or named params). Also `'?' * n` placeholder-list construction (`','.join('?' * len(ids))`) must become `','.join(['%s']*n)`.
- **`MAX(a, b)` scalar** (post_service.py:726, posts.py:578) — SQLite `MAX(x,y)` → PG `GREATEST(x,y)`. (Not in the tag vocabulary; flagged inline.)
- **`RANDOM()`** (community_service.py:157) → PG `ORDER BY random()`.
- **`NULL_ORDERING`**: `posts.created_at`, `comments.created_at`, `highlights.created_at`, `search_history.created_at`, `library_files.created_at` are declared `TIMESTAMP DEFAULT CURRENT_TIMESTAMP` (nullable, no explicit NOT NULL). SQLite sorts NULLs first on ASC; PG sorts NULLs last on ASC. Every `ORDER BY <nullable-timestamp>` flips for any NULL rows. In practice these columns are always populated by the default, so the risk is low — but the port must either add `NOT NULL`/default, or add explicit `NULLS FIRST/LAST`.
- **`TYPE_STRICTNESS`**: two `CASE … EXISTS … ELSE 0 END` expressions (post_service.py:284, :443) mix boolean and integer branches — PG rejects this. Cast the `EXISTS` branch with `::int`, or use `CASE WHEN … THEN 1 ELSE 0 END` around a `COALESCE((SELECT …), 0)`. Also `ORDER BY (m.user_id = ?) DESC` (community_service.py:218) uses a boolean expression — PG needs `ORDER BY (m.user_id = ?)::int DESC` or a CASE.
- **`rowid`** (community_service.py, 5 occurrences): `community_members` has composite PK `(community_id, user_id)` and no surrogate id, so `rowid` is its tiebreaker. PG has no `rowid`; the migrated table needs an explicit monotonic column (e.g. `id BIGINT GENERATED …`) or a `joined_at`-only ordering (which loses the stable tiebreak).
- **FK enforcement**: SQLite only enforces FKs when `PRAGMA foreign_keys=ON` is set per-connection (db.py:16,24). PostgreSQL enforces them always. Baseline `PRAGMA foreign_key_check` found pre-existing orphaned rows (likes/comments/highlights/posts referencing missing users) — the data-transfer phase must clean/defer these or load with constraints disabled. See PG_MIGRATION.md.
